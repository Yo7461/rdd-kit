# Roadmap-driven development (/roadmap)

A skill for running the development loop from a revisable roadmap and a current-position file instead of a specification finished up front. The spec is not written ahead of the code — it is maintained as a record of what the system currently guarantees. Records split into four layers:

| Layer | Files | Nature |
|---|---|---|
| Intent | `roadmap/roadmap.md` | What to do next. Rewrite freely. Don't record history here. |
| Now | `roadmap/status.md` | Where things stand, written for the person — `Now` in five fixed frames (their labels: `references/schemas.md` § Template: status.md (root)), then `Next` for the next session (paths, IDs, counts). Rewritten in full every time. 60 lines or fewer, not counting the `Phase Index` section. |
| Spec | `roadmap/spec/**` | What the system currently guarantees (map, contracts, invariants). Rewritten to follow reality — the code and tests are the truth. |
| Fact | `roadmap/phases/**` `roadmap/research/` `roadmap/experiments/` `roadmap/assets/` | What happened and what was learned. Append-only and immutable once closed. The reasons behind roadmap changes live here too. |

The records assume a single writer: one session open at a time (`open_session` is a single scalar, and a second open session is an FM-3 error). Reconciling parallel writers — branches merging records, several agents at once — is a non-goal.

## Subcommand dispatch

Read `references/workflows.md` § Common rules (what every subcommand shares — sessions, recording as you go, the lint windows, what the person reads, deferring to the user, the Next block) and then the matching section **before** acting on the argument. Read the matching template in `references/schemas.md` before creating or editing any file.

| Argument | What it does | Section in workflows.md |
|---|---|---|
| `init` | Interview → outline of the whole course → detail of the next one or two phases → one question (the `Vision`, every phase's `goal` and `why`, the next phases' `outcome`) → generate `roadmap/` | init |
| `start` | Start a session. Print the start block — the phase's outcome, this session's Plan, and whether anything is asked — and proceed; ask only under the four conditions of start step 6. Then run the work with the procedure for the phase `type` (build / research / experiment / decision), and close automatically once the work reaches a stopping point. | start, Procedures by phase type |
| `close` | End the session. Finalize the records → update status → commit → decide the next action. Normally runs automatically at the end of `start` — call it alone only after an interruption or a missed close. | close |
| `replan <topic>` | Revisit the roadmap. The topic arrives as the argument. | replan |
| `phase close` | Have the acceptance criteria verified by a context that did not do the work → draft the next phase's `goal` / `why` / `outcome` (with its `acceptance` as the appendix) → ask the user once (accept the outcome or change the plan, and approve them) → summarize the phase → detail and activate the next phase | phase close |
| `status` | Read back the current position (read-only) | status |
| `doctor` | Consistency check of `roadmap/` — the mechanical checks (references, bidirectional references, front matter, size limits, IDs, text anomalies, git, and the structure and placement of the files — all 35 rules) go to `roadmap-lint`, and the semantic checks (contracts against the implementation, records against measurements) stay with Claude (read-only). A green lint means the records are well-formed, not that they are true. | doctor |
| (no argument, or ambiguous) | Follow `next_command` in `roadmap/status.md`. Propose `init` when there is no `roadmap/status.md` (when `roadmap/` exists without it, say so — `init` asks before generating into it). | — |

There is no separate command for research or experiments. Both are planned in roadmap.md as phases (`type: research` / `experiment`), and `start` runs them.

## Ground rules

1. **Read before writing** — At the start of work, read `roadmap/status.md`, then the active phase in roadmap.md, then the phase `status.md`, then `spec/map.md` (map and invariants), in that order, and then `.roadmap-lint.json` beside `roadmap/` when the project has one (ground rule 10). Don't write code before that.
2. **Every change inside a session (`S####`)** — Don't touch anything under `roadmap/` or in the project's code while no session is open. `replan` and `phase close` are no exception — open a short session automatically when none is open. The only exceptions are `init` (it runs before sessions exist) and the small-fix route right after `close` (see `references/workflows.md` § Common rules).
3. **Where history lives** — Don't record change history or the reasons for a change in roadmap.md — put them in the current session log's `Roadmap Changes` and collapse it to one line in the phase `status.md` (a phase's `why:` is intent — why the phase exists — not history).
4. **The spec is an index of reality** — Keep the truth in the code, the tests, and machine-verifiable artifacts (an `openapi` document and the like); the spec carries only the map and the contracts (`C####`). When the spec and reality disagree, reality wins — fix the spec. Give every contract a `verified_by` (a test reference), and write `manual` when no test can cover it.
5. **IDs are permanent** — Don't reuse, renumber, or delete `P####` / `S####` / `R####` / `E####` / `B####` / `C####` / `D-P####-####` (a retired contract's entry may go, but its number stays vacant). Retire a phase as `dropped` — a tombstone, not a deletion. Don't rewrite closed session logs or artifact files that are already `done` — the only exceptions are a typo or notation fix that doesn't change the meaning and a cross-reference added to the front matter (`superseded_by`, `see_also`). When a conclusion or a number is overturned, point `superseded_by` at the newer one.
6. **Size limits** — `status.md` 60 lines (the `Phase Index` section is not counted), `spec/map.md` 80 lines, a contract file 200 lines, `roadmap.md` 200 lines, `Outcome Summary` 10 lines, `Session Log` one line per session. Detail only the active phase and the next one or two, and fold a phase that has gone `done` back to its heading plus a one-line `goal`. These numbers are the defaults, and a project may set its own (ground rule 10).
7. **A Next block ends every command — once** — Offer one recommended command as the last thing the command prints, and save the same string to `next_command` in `status.md` (`status` and `doctor` display it without saving). A reply that ends before the command does — waiting for a reviewer, a verifier, or the person — carries the in-progress notice instead and saves nothing; while the question tool is asking, it carries neither (`references/workflows.md` § The Next block).
8. **Evidence assets stay tracked** — Put the measurement scripts and generation steps that an `R####` / `E####` `Method` refers to under `roadmap/assets/<ID>/` (tracked in the repository) before marking it `done`. Don't leave references to volatile locations such as scratchpad in a file that is already `done` — the evidence has to stay reproducible. For large data that can be regenerated (a benchmark corpus and the like), keep the generation script and the reproduction command instead of the data itself.
9. **Defer to the user at a conflict** — The moment a judgment would overturn or contradict what the records already settle (a decision, a contract, a measured result), or fork observable behavior, stop settling it alone: write the point down and put it to the user in one batch at the next checkpoint — the start block printed at `start`, a design or draft review, right before `close` — each point starting from what it does to the finished product (the five required elements of a point, the exact triggers, and what Claude may settle alone: `references/workflows.md` § Defer to the user (when to ask)).
10. **The project's configuration sets the effective value** — Every number and vocabulary this skill prints is a default: the limits in ground rule 6, the shelf life of a `Parking Lot` / `Deferred` item (GIT-7, 30 days), the commit labels in `references/schemas.md` § Commit convention, the volatile locations in ground rule 8, and the file names `FILE-1` allows. When a `.roadmap-lint.json` sits beside `roadmap/`, whatever it sets under `rules.<RULE-ID>.options` replaces the matching default, and **the effective value is what a record has to satisfy** — write to it rather than to the number printed here (in a project that sets `SIZE-1` to 100, `status.md` is written to 100 lines, and at 40 it is written to 40 — the `Phase Index` section outside the count either way). A value the lint reports as ignored (the wrong shape — a limit written as `"80"`, say — or an entry a rule cannot use) does not count, for the lint and for what to write alike: that option keeps its default, or that entry is left out of its list while the rest applies, until the value is fixed. A rule turned off with `enabled: false` stops governing what to write. `sinceCommit` is the one setting that changes nothing here: it bounds how far back a commit rule reads history, not what to write — and it is set per rule (GIT-2, GIT-4, GIT-5, and GIT-6 each read their own). Which rule ID governs what: `references/workflows.md` § doctor.
11. **The person approves phases, not sessions** — What the person approves as a matter of course is a phase: its `goal`, its `why` (what the finished product lacks without it), and its `outcome` (what the person sees or can do once it is over) — at `init` (the `Vision`, the `goal` and `why` of every phase, the `outcome` of the next one or two) and at every `phase close` (the next phase, in the same question that accepts the outcome of the phase that just ended). The acceptance criteria are the AI's checks: shown as an appendix, and verified at `phase close` by a context that did not do the work. Inside a session the start block is printed and the work proceeds (`references/workflows.md` § start step 6); the person is asked under ground rule 9, for a contract draft that forks observable behavior, for `doctor` findings left unaddressed, and before any operation that changes the development machine (`references/workflows.md` § Changing the development environment, and blockers that come from it) — and also for the guard rail of `start` (asked before a session opens), for the choice in a decision phase, for a replan, and for a blocker only they can clear.
12. **What the person reads keeps one shape** — Everything a command prints for the person — the block that opens a session, the material before a question, the report that ends a command, a notice — is built from the same seven parts, in the fixed skeleton of its scene, with one word per thing, in the user's language. A record key (`goal`, `acceptance`, `depends`) is never printed as a label, and a printout takes no section its skeleton does not have (`references/workflows.md` § What the person reads).

## The Next block

```
─ Next ──────────────────────────────
Recommended: /roadmap start — S0015: continue the resolver implementation
```

Print it inside a code fence, once, as the last lines of the command. The `Recommended:` label is part of the file format and stays in English, like the headings and the front matter keys — the one-line reason after it follows the user's language.

How to decide: the command ended with a session left open at the user's request → `close` / a premise broke or a judgment is needed → `replan <one-line topic>` / every acceptance criterion in the phase is met → `phase close` / on plan → `start`. See `references/workflows.md` § Common rules for the exact decision table.

A reply that ends while the command is still running — waiting for a reviewer, a verifier, or the person — ends with the in-progress notice, not with a Next block; while the question tool is asking, it ends with neither (`references/workflows.md` § The Next block).

## Language and format

ALWAYS write generated records and every reply to the user in the user's language — the language the user writes in, not the language of this skill. Headings, front matter keys, IDs, and state values stay in English exactly as the templates spell them; everything written inside them (prose, summaries, goals, acceptance criteria, session notes) goes in the user's language. These records are read by the user far more often than by Claude, so a record in the wrong language is a broken record even when its structure is perfect.

What is printed for the person follows the same rule one step further. A record key (`goal`, `why`, `outcome`, `acceptance`, `depends`) is a key, not a label: print the label the words table gives (`references/workflows.md` § What the person reads), in the user's language. A state value (`draft`, `active`) is the record's spelling in the same way — the table gives the word to print for the state of a phase and of a contract. The table fixes the Japanese words, so a Japanese-language project reads the same words from its first printout on; a project that wants other words writes them in its CLAUDE.md.

The format is Markdown with YAML front matter (contract entries are YAML blocks with fixed keys). With git, commit as `[S####] <message>` (see `references/schemas.md` § Commit convention); without git, skip the commit steps (see `references/schemas.md` § Working without git).
